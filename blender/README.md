# Maxi 77 model

A parametric model of a 1980 Maxi 77, generated by Blender Python and exported
as glTF for the portfolio scene. The boat is described by numbers in
`params.py`; the scripts turn those into geometry. Nothing is sculpted by hand,
so the shape is diffable, reproducible, and correctable by editing a value.

## Running it

    npm run model:build      # generate geometry -> .blend + .glb
    npm run model:verify     # measure the result against the class rules
    npm run model:preview    # render orthographic views -> blender/renders/

Blender is installed as a Flatpak, which has two consequences worth knowing:

- **Every path handed to Blender must be absolute.** The Flatpak's working
  directory is `/app/blender`, not the project. The npm scripts pass `$PWD`.
- **The Flatpak cannot see the host's `/tmp`.** It gets a private one. Scripts
  and outputs have to live under the project directory.

## Layout

    params.py         every dimension, each with its source
    hull.py           the hull skin and rubrail
    lib/curves.py     shape-preserving interpolation, section shapes
    lib/mesh.py       grid lofting, mirroring, welding, shading
    build_exterior.py orchestrator -- run this
    verify.py         the class rules as a test suite
    preview.py        headless renders
    refs/             reference material (not committed -- see refs/SOURCES.md)

## How the shape is controlled

Three longitudinal curves define the hull, each a short list of control points
in `params.py` interpolated by a shape-preserving cubic:

- `SHEER` -- freeboard along the length. Pinned at both ends by the class rules.
- `PROFILE` -- the centreline: stem rake, forefoot, rocker, transom.
- `HALF_BEAM` -- width at the sheer. Pinned at the class measurement station.

At each station those give a transverse section, shaped by two more curves:

- `SECTION_FULLNESS` -- the topsides and the turn of the bilge.
- `SECTION_TUCK` -- deadrise where the section meets the centreline. Above 1 is
  a flat floor, 1 is a straight V, below 1 hollows the garboards.

`SECTION_TUCK` is the one that matters, and it is not obvious why. It barely
changes the silhouette, so it looks like a detail -- but it is most of the
displacement. The first build had flat floors everywhere and came out **83%
overweight** underwater while passing every length, beam and freeboard check.

## Verification

`verify.py` measures the built mesh the way a class measurer would and checks it
against the rules. Two of its checks are worth more than the rest:

- **Waterline length** pins the overhangs.
- **Displacement** is the integral of the section shapes. Length, beam and
  freeboard only constrain the outline -- a hull can pass all of them with
  sections that are wildly wrong. If the boat floats at the right depth with the
  right volume, the sections are broadly right.

Neither is in the class rules; both come from published figures. They are the
difference between a boat that measures correctly and a boat that is correct.

What verification cannot do is tell you it looks like a Maxi 77. That is what
`preview.py` and `refs/` are for.

## The exported GLB *is* committed

`src/assets/models/maxi77-exterior.glb` is checked in, unlike the `.blend` and
the renders. Vercel builds from GitHub and has no Blender, so the exported asset
has to be in the repo -- it is the boundary between this pipeline and the app.
Rebuild it and commit the result whenever the model changes.

## The .blend is a build artifact

`build_exterior.py` regenerates it from nothing every run. Open it in the GUI to
look around and measure freely, but anything hand-edited is lost on the next
build -- changes worth keeping go into `params.py`.

Everything the build produces lands in a collection named `maxi77_generated`.
That name is stable on purpose: if hand-modelling alongside the generated
geometry is ever wanted, a separate .blend can link this collection and rebuilds
will flow through underneath the hand work. Nothing else for that workflow is
built until it is actually needed.
